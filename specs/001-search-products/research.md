# Research: 商品検索機能

## Decision: 既存の商品一覧 API に検索条件を追加する

- **Decision**: 商品検索は `GET /api/products` に任意の `keyword` と `category` クエリパラメータを追加して実現する。商品詳細は既存の `GET /api/products/{id}` を利用する。
- **Rationale**: 既存の複数形 REST エンドポイントと商品サービスを拡張でき、一覧から詳細への導線を新しいリソース種別なしに表現できるため。
- **Alternatives considered**: 検索専用 `/api/search/products` は既存リソースの責務と重複し、クライアント側で全件取得して絞り込む方式はデータ量増加時の応答とデータ漏えいリスクがあるため採用しない。

## Decision: キーワードは入力全体の大文字小文字を区別しない部分一致とする

- **Decision**: 前後空白を除いたキーワード全体を1つの検索語として扱い、商品名または商品説明に含まれるかを大文字小文字を区別せず判定する。空文字は条件なしとする。
- **Rationale**: clarification で確定した挙動と一致し、語の分割や AND/OR 解釈を導入せず、v1 の受け入れ条件を単純に保てるため。
- **Alternatives considered**: 空白分割による AND/OR 検索は、仕様・テスト・検索結果の予測可能性を広げるため v1 では採用しない。

## Decision: 商品説明を新しいスキーマ変更で追加する

- **Decision**: 商品の説明を必須の文字列属性として追加し、既存データには空文字を設定する新規 Flyway マイグレーションを用意する。
- **Rationale**: 仕様が商品説明検索と詳細表示を要求している一方、現行の `products` テーブルと `Product` エンティティには説明がない。既存マイグレーションを書き換えずに現行データと互換性を保つには追加マイグレーションが必要である。
- **Alternatives considered**: 商品名だけを検索対象にする案は FR-002 と不一致、既存マイグレーションの直接編集はプロジェクト規約違反、nullable のまま扱う案は表示・検索時の null 分岐を増やすため採用しない。

## Decision: 検索・詳細のレスポンスは DTO で公開する

- **Decision**: 検索一覧と商品詳細は商品表示用 DTO にマッピングし、Entity を API の契約として直接返さない。
- **Rationale**: プロジェクト憲章の Entity と DTO の分離規約に従い、内部属性の追加が API 応答へ意図せず波及することを防ぐため。
- **Alternatives considered**: 現行の Entity 直接返却を新機能でも踏襲する案は、憲章の API 規約に反するため採用しない。

## Decision: 検索はデータベース側で実行し、カテゴリ条件は任意で AND 結合する

- **Decision**: Repository の検索処理で keyword 条件と category 条件を適用し、両方が指定された場合は両方を満たす商品を返す。カテゴリは1値の完全一致とする。
- **Rationale**: 既存の ProductRepository を拡張して検索対象を絞り込み、仕様の組み合わせ条件と既存カテゴリの単一文字列モデルに整合させられるため。
- **Alternatives considered**: 全件取得後のサービス層フィルタは、件数増加時のメモリ使用量と応答時間が不利なため採用しない。カテゴリ部分一致は意図しないカテゴリを含めるため採用しない。

## Decision: v1 は既存の一覧順・ページ分割を維持する

- **Decision**: 新しいページ分割や並び替えは追加せず、既存一覧の順序と全件返却の振る舞いを維持する。
- **Rationale**: 仕様の対象外事項を増やさず、既存クライアントとの互換性を保つため。データ量が増えた場合のページ分割は別機能として扱う。
- **Alternatives considered**: 今回同時にページングを導入する案は、要求されていない API パラメータと UI を増やし、検索機能の受け入れ範囲を広げるため採用しない。
